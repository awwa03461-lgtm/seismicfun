    Chapter 1 Arrival meadow

    What is Seismic?

    That tower is where we’re headed. Let’s start simple.

    Seismic is a blockchain designed to keep sensitive information private.

    A is a shared record that many computers keep together. Nobody can quietly change it, which is why people use it for money.

    Most blockchains make activity easy to inspect. That is useful for transparency, but not every balance, payment, business relationship or financial position should be visible to everyone.

    Seismic lets developers build applications where sensitive information stays protected while still enforce the rules.

    Technical term EVM-compatible blockchain with native privacy

    Deep dive: what kind of chain is this? Technical

    Seismic is an -compatible Layer 1. Contracts are written in Solidity, and the docs describe the workflow as Solidity, Foundry and Viem, with privacy added.

    Privacy is native, meaning it is built into three layers of the stack rather than bolted onto one app:

    LayerWhat it does
    Seismic Solidity compiler (ssolc)Adds shielded types that compile to privacy-aware opcodes.
    Seismic networkEVM-compatible L1 whose nodes run inside Trusted Execution Environments ().
    Shielded storage (FlaggedStorage)Each storage slot carries a public/private flag enforced at the opcode level.

    Source: How Seismic Works (official docs)

    Why this matters

    Real financial systems need both verifiability and confidentiality. Seismic is designed to offer both in one place.

    Chapter 3 The Seismic Gate

    What Seismic changes

    This gate marks the edge of the protected zone. Walk through with me.

    Seismic lets applications decide which information should stay private.

    The blockchain still enforces the rules. Transactions still happen. Contracts still run.

    What changes is who can see the sensitive values inside them. A developer marks what is sensitive, and the network keeps it out of public view.

    Everything else can stay public where that is useful, such as the fact that a contract exists or that a payment happened.

    Technical term Native privacy / shielded state

    Deep dive: where the privacy lives Technical
    1. Compiler. Seismic Solidity adds shielded types. The compiler routes them to private storage opcodes.
    2. Execution. Nodes run inside , so sealed inputs are only decrypted inside protected hardware.
    3. Storage. FlaggedStorage marks each slot public or private; ordinary reads of private slots return zero.
    4. Transactions. A dedicated transaction type () carries encrypted calldata.

    Public and shielded state live side by side in the same contract. A developer chooses per variable.

    Source: How Seismic Works

    Why this matters

    Because privacy is part of the chain itself, apps don’t have to invent their own hiding tricks. They opt in using tools the protocol provides.

    Technical term Shielded types

    Deep dive: one letter, and what it really does Code

    In Seismic Solidity, the difference is written like this:

    // Ethereum: readable by anyone
uint256 balance;

// Seismic: shielded
suint256 balance;

    The s marks the value as shielded. Supported shielded types: .

    Not magic

    The letter is a signal, not a spell. Behind it, the compiler emits private storage opcodes, the node executes inside a TEE, and the RPC layer redacts shielded slots. The compiler also forbids some patterns: shielded variables can’t be public, and can’t be returned from public or external functions.

    Developers still have to avoid leaks, such as unprotected getters or gas differences. See Security & limits.

    Sources: How Seismic Works, Footguns

    Why this matters

    Apps can run real logic on sensitive numbers without broadcasting those numbers to the world.

    Chapter 5 The two vaults

    Private storage

    Two vaults. One has windows. One is sealed.

    Normal blockchain storage is designed to be readable. Seismic adds a private form of storage for shielded values.

    A contract remembers things in storage slots, a bit like numbered drawers. On a normal chain, anyone can open any drawer and look.

    On Seismic, a drawer holding a shielded value is flagged as private. Asking for it from outside returns zero, as if the drawer were empty.

    Technical term Encrypted calldata, Seismic transaction type

    Deep dive: the private transaction flow Technical
    1. The client asks the node for the network’s TEE public key (seismic_getTeePublicKey).
    2. It combines that key with the user’s key (ECDH) to create a shared secret.
    3. It encrypts the calldata with authenticated encryption (AES-GCM).
    4. It broadcasts the result as a type transaction.
    5. Inside the TEE, the node decrypts, executes, and writes results to shielded storage.

    The docs state that plaintext calldata is not visible outside the TEE: not in the mempool, block data or transaction traces.

    The cryptography, briefly Optional

    ECDH lets two parties each combine their own private key with the other’s public key and arrive at the same secret, without ever sending that secret.

    AES-GCM encrypts the message with that secret and adds a tag, so any tampering is detected.

    Sources: How Seismic Works, The Seismic Transaction

    Why this matters

    If inputs leak on the way in, private storage can’t help. The envelope protects the journey.

    Chapter 7 The Secure Chamber

    A locked room inside the computer

    Inside this chamber, the work happens where no one can look. Not even its owner.

    Imagine a locked room inside a computer.

    The computer can run calculations inside that room, but the rest of the machine, and even the person who owns the computer, is not supposed to be able to look inside.

    Seismic runs its nodes inside these hardware-protected rooms. Sealed transactions are opened and processed only in there.

    An honest note

    This design introduces a trust assumption in secure hardware and the implementation around it. It is a strong lock, not a magic one.

    Technical term Trusted Execution Environment (TEE), using

    Deep dive: Intel TDX and attestation Technical
    • Isolation. The whole node process runs inside an Intel TDX environment. The docs state the host OS, hypervisor and node operator cannot read or write its memory.
    • Remote . A new node produces a hardware-signed report. Existing nodes check it came from genuine Intel TDX hardware running the approved code measurement.
    • Key sharing. Only after attestation passes does the new node receive the network root key. Keys are generated inside the TEE and there is no API to export them.
    • Decryption. The root key derives the network’s encryption secret key, used to decrypt type calldata.

    What the docs say TEEs do not protect against

    • Hardware side-channel attacks (an active research area).
    • Bugs in the approved node software, which the TEE would faithfully run.
    • Transaction metadata such as sender, gas and target contract.
    • Guessable low-entropy values (see Security & limits).

    Source: How Seismic Works: Enclave and TEE guarantees

    Why this matters

    The locked room is what lets Seismic compute on private data with ordinary smart-contract code. It is also where much of the trust sits.

    Technical term Signed Reads

    Deep dive: why a plain read isn’t enough Technical
    • On standard EVM chains, anyone can put any address in the from field of a read call and impersonate it.
    • Seismic zeroes the from field of a plain eth_call, so msg.sender is the zero address.
    • A signed read is a Seismic transaction (type ) sent to eth_call with signed_read = true. The node recovers the signer and uses it as msg.sender.
    • The response is encrypted to the caller’s key, so someone intercepting it can’t read it either.
    • A signed read can’t be replayed as a write, and a write can’t be reused as a signed read.

    Source: Signed Reads (official docs)

    Why this matters

    Privacy is only useful if the right people can still see their own information.

    Technical term Intelligence Contracts

    Deep dive: access rules written in the contract Code

    An Intelligence Contract stores data shielded by default and adds gated functions that reveal it only to callers with the right role. The docs’ example uses OpenZeppelin AccessControl:

    function complianceBalanceOf(address a)
  external view returns (uint256) {
  require(hasRole(COMPLIANCE_ROLE, msg.sender));
  return uint256(balanceOf[a]);  // suint256 in storage
}
    • Owners read their own balance via a signed read; auditors and compliance officers call role-gated functions, also via signed reads.
    • Balances never leave shielded storage; each answer is encrypted to the one caller.
    • Role assignments are ordinary public state, so who holds access is auditable.
    • In the example, a frozen-account flag is deliberately public so counterparties can see it.

    Source: Intelligence Contracts tutorial

    Why this matters

    Regulated finance needs someone to be able to check. Selective disclosure allows that without making everything public.

    Technical term Encrypted events with cryptographic precompiles

    Deep dive: how a contract encrypts an event Technical

    Shielded types can’t be used as event parameters; the compiler rejects them. The docs’ tutorial instead encrypts the amount and emits opaque bytes:

    1. Derive a shared secret with the recipient using the ECDH precompile.
    2. Derive an encryption key from it with HKDF.
    3. Encrypt the amount with AES-GCM and emit it as bytes.
    4. The recipient decrypts off-chain with their own key.

          Security and limits Stillwater, at dusk

          Trade-offs, explained calmly

          Every design has trade-offs. Let’s look at them calmly.

          Seismic’s privacy is strong but not unconditional. These are the conditions.

          ATrust in secure hardware

          Seismic’s privacy model depends in part on secure hardware and the software running inside it.

          Risk categories Technical
          • Hardware vulnerabilities in the TEE platform.
          • TEE side channels, an active research area.
          • Implementation bugs in approved node code, which the TEE would run faithfully.
          • Attestation issues: the check that nodes run approved code must itself be sound.
          • Operator and infrastructure assumptions around how nodes are run.

          BClues from how much work is done

          Even if a value is private, an app can accidentally reveal clues through how much work it performs.

          Try it: guess a hidden yes/no from the gas bill

          Your guess for the hidden flag:

          Gas is public. Watch what it gives away.

          Illustrative gas numbers.

          Common leak patterns Technical
          • Branches on a shielded value that do different amounts of work.
          • Loops whose length depends on a shielded value.
          • Exponentiation with a shielded exponent (gas scales with the exponent).
          • Timing and resource patterns visible in execution traces.

          The docs recommend constant-cost patterns, such as a ternary with equal work on both sides, or fixed-length loops with equal-cost no-ops.

          Source: Footguns

          CSecrets with few possible values

          Values with only a few possible choices can sometimes be guessed, even when marked private. Think true/false, a small list of options, or a tiny known range.

          Why guessing works Technical

          Shielded values are still committed into the storage Merkle trie at a publicly known slot, without a per-slot salt. An attacker can try each candidate value and compare against the public commitment; the docs note proof endpoints make this easier. Mitigation: store a salted commitment for small-domain secrets that are only checked by equality. High-entropy values, such as balances that accumulate over time, are not practically guessable.

          DUsing the wrong transaction path

          Developers must use the private transaction flow. If sensitive values are sent through a normal public transaction, they can be exposed.

          Details Technical
          • The docs state nothing currently enforces that functions with shielded parameters are called with a type transaction; a regular call shows the values in plaintext. They plan to tighten this.
          • Contract-creation calldata is not encrypted, so secrets must not be passed to constructors.
          • Shielded literals are embedded in public bytecode.
          • A view function that returns unshielded data without access control leaks it to anyone.

          These are developer footguns, not evidence that the privacy model is broken.

          EMetadata

          Confidential data can be protected while some transaction metadata remains public: sender, target contract, gas used, and the fact that a transaction happened.

          Why this matters

          Knowing the limits is what lets you use privacy well. Trust is earned by being specific.

          Comparison Stillwater

          Seismic and other privacy approaches

          Three families of techniques, three different sets of trade-offs.

          Prove something is true without showing the data.

          Possible strengths

          • Cryptographic verification
          • Strong proof-based models

          Possible trade-offs

          • Application complexity
          • Specialized circuits and tooling in many systems

          Do math on a locked box without opening it.

          Possible strengths

          • Computation directly on encrypted data

          Possible trade-offs

          • Heavy computational overhead in many current implementations

          , Seismic’s approach

          Do the work inside a locked room built into the hardware.

          Possible strengths

          • Familiar programming model
          • Flexible computation
          • EVM-friendly developer experience
          • Lower friction for ordinary contract logic

          Possible trade-offs

          • Trust in secure hardware
          • Hardware and attestation assumptions
          • Side-channel considerations

          These are different trust and performance models, not a simple winner/loser comparison.

          Why this matters

          Choosing a privacy system means choosing what you trust. Seeing the options side by side makes that choice visible.

            Is Seismic completely anonymous?

            No. Seismic is designed for confidential computation and shielded data, but some transaction metadata can remain public.

            Is Seismic EVM compatible?

            Yes. Its design is intended to preserve a familiar Ethereum-style development experience while adding privacy capabilities.

            Is everything private automatically?

            No. Developers must correctly use shielded types, private transaction flows, access control and privacy-aware application design.

            What is a shielded value?

            A value the application can use while normal public reads are prevented from revealing it.

            What is a TEE?

            A Trusted Execution Environment: a protected, hardware-backed area used to process sensitive data in isolation.

            Why use Intel TDX?

            Seismic uses Intel TDX as part of its secure execution model. It provides hardware-backed isolation for confidential execution, plus remote attestation so nodes can check each other run approved code.

            Can authorized parties access private data?

            Applications can be designed with controlled access rules so that selected users or compliance roles can view specific information.

            Does Seismic replace ZK?

            No. Seismic uses a different privacy model with different trade-offs.

            Does Seismic eliminate MEV?

            No such claim is made here. Privacy can reduce some of the information exposure that certain MEV strategies rely on, but that is not the same as eliminating all MEV.
